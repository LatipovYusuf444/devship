# DevShip design

Version 1.4 adds opt-in checksMode=final while the default both mode preserves existing pre-commit and post-merge validation. Final mode stages/commits/fetches/merges before running every configured or rediscovered check once on the final code. Local commits may exist when checks fail, but publishing remains gated by successful final checks and the existing HEAD/branch/clean-state/history/preflight guards. No check-result cache or parallel builds are used. Conflict failure avoids spending time on checks. The two unpublished-history scans share a run-local Set of successfully inspected immutable blob OIDs; entry type/path rules are applied before consulting it. No cache persists across runs. Each completed check reports elapsed seconds. The user-app source, package scripts, lockfiles and backend are not modified by this optimization.

Version 1.3 adds operational failure notifications after validated feature-branch preflight and while holding the repository lock. Shipping tracks the current phase and catches the original error exactly once, notifies, rethrows the same error and releases its lock. Dry-run/preflight/config/lock failures and post-publication errors do not trigger failure alerts. A structured merge report is attached to the error even if its separate JSON report cannot be saved. Conflict alerts render metadata without file bodies. Check failures preserve both stdout and stderr so warnings cannot hide diagnostic errors. Alert diagnostics select bounded compiler/test error and file-location lines, excluding source frames, diffs, inline programs and known secrets. This is a heuristic, not a guarantee against arbitrary secret-bearing scripts. Large alerts use xato-hisobot.txt and the same durable recipient/topic-bound retry mechanism. No Git recovery, merge resolution, push retry or user project modification is performed by notification handling.

Universal, locally installed Node.js CLI for trusted Git projects. Node >=22 and Git >=2.30; no runtime dependencies. Uzbek console and guide. All operations run at the repository root even from a subdirectory.

Flow: exclusive repository lock; reject protected/detached/unborn branches, in-progress operations, shallow clones, submodules, ambiguous remotes and unsafe Git configuration; load strict JSON configuration; identify explicit build/test tasks; inspect all pending files and staged state; run checks; verify the snapshot did not change; stage explicit literal paths; commit with deterministic message; fetch origin heads; scan unpublished history; merge remote feature branch then origin/main; rediscover checks; run checks again; require clean tree and unchanged branch/HEAD; rescan unpublished history; push one explicit full branch refspec with tags and mirror disabled.

Defaults protect main, master, develop, development, production, staging, release and release/**, plus the selected base branch. Additional protections are additive. No force push, reset, clean, stash, automatic conflict resolution, history rewriting, dependency installation, or hook bypass. Existing partial staging fails closed. Nonignored secret paths/content fail closed, including already committed unpublished history. Common build output paths and configured exclusions stop staging; users must resolve or ignore them explicitly. Symlinks/submodules and oversized new blobs require manual handling. A no-check project needs explicit allowNoChecks in config. Maven verify; Gradle build; Node declared test/build scripts via the detected package manager. Mixed root ecosystems all run; nested projects need explicit checks.

Changes made by checks abort before commit. Assume-unchanged and skip-worktree index flags are rejected, including ordinary sparse checkout, to ensure tests see the committed content. Fetch ignores configured refmaps, disables tag pruning and automatic maintenance, and only updates its explicit remote-tracking namespace. A failing merge leaves Git's recoverable conflict state. Failed final checks leave local commits and stop push. Push races are rejected by ordinary Git fast-forward protection. Clean trees still sync and validate; identical local/remote branch skips redundant push. Unpublished feature branches receive upstream on first successful push. Fetch and push must resolve to the same single remote URL.

Optional AI is intentionally unnecessary: deterministic conventional messages use changed file categories; -m supplies a custom message. No credentials or source code are sent to AI services.

Version 1.2 adds optional Telegram group notifications. Async shipping parses push porcelain output and only notifies when the exact intended branch is newly created or updated. Dry runs, failures, conflicts and up-to-date results never notify. Reports compare the fetched remote feature tip (or base for an unpublished branch) with the pushed HEAD: commits/authors, filenames/statuses, project, branch and local/UTC timestamps. Plain text has no link previews. Long reports use a Unicode-safe summary plus a full metadata text attachment; file contents are never sent.

Interactive setup hides token input and disables readline history. It verifies the bot, pairs an exact random command with one group/topic, and confirms the recipient. Manual Chat ID is supported. Setup never deletes webhooks, acknowledges update offsets, or sends a test message automatically. Credentials live outside Git repositories, beside global configuration. Windows uses DPAPI CurrentUser through .NET with stdin input; other platforms use mode 0600. Repo configuration can disable notifications but cannot redirect their recipient or supply credentials. HTTPS requests have a fixed Telegram host, no redirects, a timeout and safe errors.

A metadata-only outbox under the working tree's Git directory records delivery before networking. Successful summary/document IDs are checkpointed; explicit, repository-locked retry resumes incomplete delivery and requires the original group/topic. A lost API response or receipt write can cause a duplicate on manual retry; uncertainty is reported. Telegram errors leave successful Git publication successful. Tests use fake API responses with real local Git fixtures and native Windows credential round-trips; no live group is contacted.

Tests use real temporary repositories and local bare remotes, plus pure unit tests for detection, config, command quoting and secret policy. CI covers Windows/macOS/Linux with Node 22 and 24. Current-host verification is distinguished from CI coverage.

Version 1.1 adds read-only conflict diagnostics before failing the merge step. The current/incoming refs and pre-merge commit IDs are captured explicitly. Unmerged index stages identify every file and its conflict type. Text marker blocks provide working-file line ranges; binary, renamed or deleted paths without markers receive no invented line numbers. Each side is attributed to its last file-relevant commit since the merge base, with a clearly marked common-history fallback. Authors are Git metadata, not a claim about exact line authorship or branch ownership. Source contents are never included in the structured report. A unique JSON report is written exclusively under the working tree's Git metadata directory; failure to write does not weaken the fail-closed no-push behavior. Merge stdout and stderr are preserved for non-conflict failures too.
